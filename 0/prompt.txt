## #48 "Bound Entire transcript memory while streaming": **SAFE TO MERGE**

**Blocking findings:** none.

**What I confirmed:**

  - main runs out of memory with a 64 MB heap cap; #48 finishes inside a 24 MB cap.
  - With no cap, the heap grows by 4.5 MB on #48 for a single 110 MB line, against 319 MB on main.
- **A huge single line costs nothing extra.** `boundedLines` (`entire.ts:86`) uses one fixed 256 KiB buffer and drops the bytes of any longer line without keeping them. Line numbering, UTF-8 split across chunks and CRLF are all handled and tested.
- **Selection order is preserved.** A throwaway fuzz test ran 30 random checkpoints of 1–3 sessions, with budgets from 50 to 20,000 tokens. **Behaviour changes (not blocking):**
- **Over-long lines are skipped.** Any transcript line over 256 KiB is now skipped. A Write or Edit with a very large file body therefore loses its `[Edit] file` passage, and the reasoning before it is no longer promoted. The same applies to a pasted prompt over 256 KiB when the prompt is read from the transcript. This is rare and acceptable.

## #51 "Harden the push gate": **SAFE TO MERGE**

**Blocking findings:** none.

**What I confirmed:**
- **Fail open still holds for a dead daemon.** A connection failure mid-submission surfaces as a `TypeError` and the push goes through. A 5xx response also lets it through. Only `SubmissionTimeoutError` and 4xx errors block, at `cli.ts:84`. Tests cover all four cases.
- **Hard gates can still never be skipped.** The `skippable === false` check is still enforced by the daemon at `app.ts:141`. Moving the 409 "in progress" check ahead of it only changes the error message.
- **Slow grading now blocks, which is the right call.** Answers and skips get 120 s. If a submission times out after the developer has answered, the push is blocked with "retry git push", because the result is unknown and shouldn't count as a pass. The retry then gets the stored decision. If grading is still running at that point, the developer sees the exam again and gets a 409 "already in progress" after answering. That's safe but clunky.
- **Attestations can't be doubled.** The decision receipt is written first, the review is then marked done, and only then are attestations appended to the ledger.
  - If the receipt write fails, the ledger is untouched and a retry grades again.
  - If the append fails, the review is already done, so a resubmit gets a 409 and doesn't append twice. Tests cover both paths.
  - A daemon crash between the receipt and the append can lose that review's attestations; the PR documents this. Main's order risked doubling them instead.
- **Escape stripping is complete.** I probed it with CSI, OSC (BEL and ESC-backslash terminated, including clipboard OSC 52), C1 characters (0x9B, 0x9D), DCS and plain ESC sequences. No control byte survived. Two cosmetic leftovers:
  - The payload of an OSC with spaces or of a DCS can stay as visible text (e.g. "y evil title").
  - Tabs are deleted, which joins the words either side; right-to-left override characters (U+202E) pass through.

**Not blocking:**
- **A ledger-append failure still lets that one push through.** It returns a 500, which the client treats as an infrastructure failure, even when the verdict was a reject. Main behaves the same way, and with #51 the decision now holds on retry. Suggested follow-up: catch the append error in `app.ts:129` and return the review anyway.
- **Windows path check (`cli.ts:136`).** It's no worse than main. However, `realpathSync` doesn't normalise drive-letter case or 8.3 short names (e.g. `RUNNER~1`) on Windows. Suggested follow-up: `realpathSync.native` plus a case-insensitive comparison on win32. I couldn't run the junction-based symlink test on Windows here, but junctions don't need admin rights, so it should work in CI.

## #43 ledger sync — MERGE AFTER FIXES

**Blocking**

1. **One bad note from any teammate breaks the Fog and reviews for the whole team, permanently.** `packages/engine/src/ledger/notes.ts:21` calls `JSON.parse(row)` without a try/catch. That was harmless while notes were local only. Now `sync.ts:29` merges in teammates' notes with a union merge, so a non-JSON line (old tool, typo, hand edit) reaches every clone and can never be removed.
   - **Confirmed with a throwaway test:** clone B adds `notes add -m "not json"` and syncs; A syncs; `readLedger(A)` throws. `/v1/fog` then returns 500 and `POST /v1/reviews` returns 500.
   - Pushes still go through (the hook fails open), but Viva silently stops reviewing for everyone.
   - **Fix:** catch parse errors per line and skip bad lines. Add a regression test: a malformed teammate line, then check that `/v1/fog` returns 200.

2. **The 1.5-second budget can't fit a real sync with GitHub, so the feature won't work against the team's remote.**
   - **Measured on this machine**, with the PR's exact options over SSH: `git fetch` of `main` took 1.49–1.51s (3 runs), and `ls-remote` took 1.47–1.58s.
   - `sync.ts:11` gives fetch, merge, push and the retry one combined 1.5s deadline. So background publishing and `viva ledger sync` will almost always fail and print "unavailable; retry later".
   - Meanwhile each review start (`app.ts:85`) and each Fog load (`app.ts:229`) still waits about 1.5s for a fetch that usually times out.
   - The deadline also covers the local `git notes merge`, which gets killed if the fetch used up the budget.
   - **Fix:**
     - Apply the deadline only to `fetch` and `push`.
     - Give background publishing and `viva ledger sync` about 15–20s.
     - Stop awaiting the fetch on review start and Fog loads: run it in the background, at most about once a minute per repo.

**Non-blocking**
- **SSH override (`sync.ts:22`):** the default `GIT_SSH_COMMAND` overrides the user's `core.sshCommand` (e.g. a custom key) and `GIT_SSH` (plink on Windows), so login fails silently. Only set it when none of the three is already set.
- **Windows (not tested; no Windows machine):** Node's `execFile` timeout kills only `git.exe`. Its `ssh` or `git-remote-https` child processes can keep the pipes open, so the call may not return at the deadline. There is also no lock-file cleanup on kill, so a stale `refs/notes/viva.lock` could make the next attestation append fail. The PR's stalled-remote test only proves macOS/Linux. Suggest wrapping the call in an outer `Promise.race` deadline.
- **Lock is per process (`lock.ts:4`):** `viva ledger sync` (the CLI process) racing a daemon append could lose an update. I believe git updates the notes ref without checking its old value, but I haven't verified that. The window is very small.
- **Trust (by design):** anyone who can push to `origin` can add attestations under any `person` name. That lowers that person's risk score, which can approve their push as `earned-trust` with no exam. This now applies team-wide and can't be undone. Worth listing in Known gaps.
- **Privacy:** attestations (names, file paths, scores, review IDs) are published to `origin` automatically after every exam. On a public repo that makes them public.
- **Fog polling:** if the web UI's live event stream drops, it polls `/v1/fog` every 2s, and each poll now does a network fetch.
- **Scope of the push is correct:** it pushes only `refs/notes/viva`, only to `origin`, with `--no-verify` (no hook recursion; the PR's rejecting-hook test covers this) and `--no-follow-tags`. Adding `--recurse-submodules=no` to the push would be a minor extra.

## #44 demo resilience — MERGE AFTER FIXES (one small fix)

**Blocking**

1. **Network errors no longer try the fallback model.** `resilient.ts:15-19`: `isCapacityError(new TypeError("fetch failed"))` returns false, so a DNS failure or connection reset throws straight away. It returns a plain 500, not the labelled 503, and never tries `GEMINI_FALLBACK_MODEL`.
   - Before this PR, the same setup did try the fallback model on network errors (`GeminiProvider(..., fallbackModel)` caught fetch failures and moved to the next model).
   - **Confirmed with a stub test:** the fallback is called 0 times.
   - Pushes still fail open. But this is a regression in the exact case the PR is meant to handle, such as venue wifi dropping.
   - **Fix:** treat a fetch `TypeError` (or `cause.code` such as `ECONNRESET`, `ENOTFOUND`, `ETIMEDOUT`) as a capacity error, and add a test.

**What I verified as safe**
- **Opt-in:** the cache does no I/O unless `VIVA_LLM_RECORD` or `VIVA_LLM_REPLAY` is set. `.viva/cache/` is gitignored, writes are atomic with 0600 permissions, and nothing is logged.
- **Cache key:** it covers provider id, model, stage name, system prompt, user prompt (which includes the transcript) and the full JSON schema. Replay re-validates against the current zod schema, and fallback results are never cached.
- **Errors surface:** checks and grading use `Promise.all`, so a failed model call can't be silently dropped. `ModelUnavailableError` becomes a 503, which the gate treats as ≥500 and fails open; `runExam` rethrows correctly.
- **Gates:** prechecks and the injection scan run before any model call, so hard gates are untouched. There is no automatic mock fallback, and `MeteredProvider` still counts replayed tokens.

**Non-blocking**
- **Cache folder (`app.ts:40`):** by default it is `.viva/cache` in whatever directory the daemon was started from. Started inside another repo, the cache (model output about that code) isn't gitignored there. A planted cache file with a matching key is replayed as trusted (confirmed), and the key for check prompts can be computed from the diff. Default it to the Viva checkout, or require `VIVA_LLM_CACHE_DIR`.
- **Interaction with #43:** grades from replay create real attestations, and nothing marks an individual review as replayed (only `/v1/health` shows a running total). Once #43 is merged, a rehearsal in the README's "disposable copy" would publish those attestations to the team's `origin`. The README should say to remove `origin` in that copy.
- **Demo caveat:** offline replay only matches word-for-word identical answers, so spoken answers will miss the cache. Each miss returns a 503 and the push goes through unexamined (fail open).
